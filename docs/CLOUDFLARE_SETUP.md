# Deniz Estate: GitHub → Cloudflare → Telegram и Resend

[Подтверждено] Сайт использует HTML/CSS/JavaScript и собственный `scripts/build.mjs`, без Vite и React. Cloudflare Worker находится в `cloudflare/worker.mjs`, статическая сборка — `dist`.

| Поле | Значение |

[Подтверждено] `npm ci` устанавливает зависимости из lockfile. `npm test` выполняет проверки. `npm run check:cloudflare` собирает Worker в режиме dry-run, без публикации. В локальной рабочей папке `npm run deploy` включает сборку; при GitHub-интеграции Cloudflare использует команды из таблицы.

[Подтверждено] Первый деплой предназначен для проверки внешнего вида: `LEADS_ENABLED=false`, SEO noindex. Форма не выдаёт подтверждение сохранения, если сервер не настроен. Для рекламы нужно сначала пройти следующие шаги.

## Постоянное хранилище заявок D1

[Подтверждено] Заявка сначала записывается в D1 с AES-256-GCM шифрованием контактов и ответов. Telegram и email получают уведомления после записи. Состояние доставки хранится отдельно для каждого канала. Никакие персональные данные не передаются в открытые логи или параметры URL.

1. Создать D1 через панель Cloudflare или командой `npx wrangler d1 create deniz-estate-leads`. Само наличие имени в коде базу не создаёт.
2. Добавить в `wrangler.jsonc` рядом с `assets` блок с фактическим ID созданной базы:

```json
"d1_databases": [
  {
    "binding": "LEADS_DB",
    "database_name": "deniz-estate-leads",
    "database_id": "ID_СОЗДАННОЙ_БАЗЫ",
    "migrations_dir": "migrations"
  }
]
```

3. Применить схему: `npx wrangler d1 migrations apply deniz-estate-leads --remote`. Для локальной проверки вместо `--remote` используется `--local`.
4. Сохранить конфигурацию с настоящим ID в GitHub. ID базы не является секретным ключом. Не оставлять D1 только как ручную настройку панели: конфигурация репозитория должна соответствовать деплою.

## Секреты и получатели

[Подтверждено] Все значения ниже добавляются в Cloudflare Workers → Settings → Variables and Secrets как Secrets. Их нельзя писать в HTML, клиентский JavaScript, GitHub Issues или исходники.

| Имя | Значение |
| --- | --- |
| `LEAD_ENCRYPTION_KEY` | Случайный ключ из 64 шестнадцатеричных символов, 32 байта |
| `TELEGRAM_BOT_TOKEN` | Токен созданного через BotFather бота |
| `TELEGRAM_CHAT_ID` | ID личного чата или закрытой группы для заявок |
| `RESEND_API_KEY` | Ключ Resend с разрешением отправки писем |
| `LEAD_EMAIL_FROM` | Отправитель с домена, подтверждённого в Resend |
| `LEAD_EMAIL_TO` | Почтовый адрес получателя заявок |

[Подтверждено] Ключ шифрования можно сгенерировать локально: `openssl rand -hex 32`. Сохраните его в менеджере паролей. Потеря ключа делает старые заявки недоступными; замена ключа без переноса данных не поддерживается. Для локальных секретов скопируйте `.dev.vars.example` в `.dev.vars`; последний игнорируется Git.

[Подтверждено] Перед отправкой в личный Telegram-чат пользователь должен открыть бота и нажать Start. Для группы добавьте бота в выбранную закрытую группу и используйте её chat_id. Отправка уведомлений и связь с самим клиентом — разные действия: бот уведомляет менеджера, а менеджер связывается с клиентом выбранным в квизе способом.

[Подтверждено] В Resend нужно подтвердить домен отправителя и указать фактический email получателя. DNS-записи берутся только из панели Resend; текущие MX, SPF и DKIM домена нельзя заменять произвольными шаблонами.

## Включение и проверка

1. После настройки D1, ключа шифрования и обоих каналов изменить `LEADS_ENABLED` в `wrangler.jsonc` на `"true"`, закоммитить и отправить в GitHub.
2. Отправить отдельную тестовую заявку с явно тестовым именем. Проверить уведомление в выбранном Telegram-чате и письмо на согласованном адресе.
3. Проверить, что повторный запрос не создаёт вторую запись, а сбой одного канала не теряет заявку. Фоновый Cron запускает повторные попытки каждые 5 минут, обрабатывая до 5 записей за запуск.
4. Подключить реальный домен; добавить `SITE_URL=https://ваш-домен` как **build variable** Cloudflare. Для preview-сборок переменную не задавать. После повторной сборки проверить canonical, sitemap, HTTPS и отсутствие noindex на основной публикации.

[Подтверждено] При недоступности Telegram/Resend заявка остаётся зашифрованной в D1, успешный канал повторно не отправляется. Сбойные отправки повторяются с увеличением интервала до часа. Защита email от повторов дополнительно использует Resend Idempotency-Key. Telegram не предоставляет такого ключа: в редком случае потери подтверждения возможен повтор уведомления; его можно узнать по одинаковому ID заявки.

[Подтверждено] Для контроля очереди в D1 можно проверить без раскрытия контактов: `SELECT telegram_status, email_status, COUNT(*) FROM leads GROUP BY telegram_status, email_status;`. Автоматические тревоги администратору пока не подключены. Срок хранения и автоматическое удаление заявок ещё не настроены.

[Требует уточнения] До сбора реальных заявок нужны утверждённые реквизиты оператора, срок хранения, юридические тексты с фактическими поставщиками (Cloudflare, Telegram, Resend) и решение по согласию. Сейчас галочка предустановлена по предыдущему указанию владельца. Рекламные пиксели и Consent Mode пока не подключены; без отдельной настройки аналитика не отправляется.

## Чистый push из локальной рабочей папки

[Подтверждено] В исходной рабочей папке сохранена локальная история экспериментов. Она не публикуется. `npm run prepare:github` копирует только разрешённые файлы проекта в игнорируемую `.github-publish`, где находится отдельный Git-репозиторий для отправки. Перед следующим push обновите этот снимок, затем выполните commit и обычный push внутри `.github-publish`. В обычном клоне GitHub-репозитория можно работать напрямую: файлов агентов в нём нет.

[Подтверждено] В публикацию не включаются `AGENTS.md`, `.agents`, `.codex`, `.hallmark`, `.taste-skill`, архив, локальные секреты, база заявок, `node_modules` и сгенерированные сборки. Локальные исторические отчёты также исключены; публикуется только эта инструкция по запуску.
